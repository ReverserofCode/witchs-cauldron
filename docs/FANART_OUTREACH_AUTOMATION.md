# 팬카페 이용 허락 요청 자동화 운영 가이드

## 지원 범위

운영자가 등록한 모잉 팬카페(`30182989`, 팬아트 게시판 `38`) 게시물만 처리합니다. 새 글 전체 수집, 과거 글 일괄 댓글, 독촉 댓글은 포함하지 않습니다. 현재 버전은 작품당 이미지 하나를 게시합니다.

작동 순서는 다음과 같습니다.

1. `/admin/fanart`에서 후보 원문과 작품 정보를 등록하고 허락 요청을 대기열에 넣습니다.
2. 별도 작업자가 전용 네이버 계정의 로그인 상태와 게시판·원작자 정보를 확인하고 요청 댓글을 한 번 작성합니다.
3. 원작자가 그 요청 댓글에 단 답변을 수집합니다. 다른 사람의 댓글이나 단순 긍정 표현으로 자동 승인하지 않습니다.
4. 운영자가 답변과 대상 이미지, 사이트 게시·크기 조정·출처 표기 허락 및 비생성형 제작 여부를 직접 확인합니다.
5. 작업자가 답변과 원문이 바뀌지 않았는지 다시 확인하고 이미지를 비공개로 준비합니다.
6. 운영자가 **실제로 준비된 이미지**를 미리 보고 승인합니다. 승인은 해당 파일의 SHA-256에 묶입니다.
7. 작업자가 로그인, 최신 답변·원문, 파일 해시와 작업 상태를 다시 확인한 뒤 공개 상태로 전환합니다.

네이버 로그인은 모든 실제 원문 조회·답변 확인·이미지 준비·게시 처리의 필수 조건입니다. 로그아웃, 세션 만료, 다른 계정, CAPTCHA 또는 제한 화면에서는 작업을 멈춥니다. 자동 로그인이나 인증 우회는 하지 않습니다. 관리자 화면에서의 대기열 등록·검토는 네이버에 직접 접속하는 동작이 아닙니다.

## 구현과 실연동의 차이

브라우저 모듈은 명시적으로 설정한 DOM 선택자를 사용하는 어댑터입니다. 저장소의 예제 선택자는 **테스트 HTML용이며 실제 네이버 로그인 화면용 설정이 아닙니다**. 격리 테스트 성공만으로 실서비스 댓글 작성에 성공했다고 판단하면 안 됩니다.

실운영에는 전용 계정의 수동 로그인, 로그인 후 실제 화면의 선택자 확인, 네이버 계정의 안정적인 카페 회원 키, 작업자와 사이트가 공유하는 DB 및 비공개 이미지 저장소가 필요합니다. 별도 작업자는 Next.js 요청 처리나 기존 사이트 배포만으로 시작되지 않습니다.

작업자는 전체 소스와 개발 도구 의존성을 설치한 별도 Node.js 22 실행 환경에서 운영합니다. 현재 Next.js 프로덕션 컨테이너는 이 CLI에 필요한 TypeScript 소스·`tsx`·Playwright 실행 환경을 제공하지 않으므로 그 안에서 `npm run fanart:outreach`를 실행하는 배포 구성은 지원하지 않습니다. DB 포트를 인터넷에 공개하거나 이미지 디렉터리를 웹 공개 폴더로 옮겨 연결 문제를 해결하지 않습니다.

## 환경 설정

| 변수 | 용도 |
|---|---|
| `FANART_BROWSER_PROFILE` | 전용 브라우저 프로필의 절대 경로 |
| `FANART_SELECTORS_FILE` | 확인된 선택자 JSON의 절대 경로 |
| `FANART_OPERATOR_MEMBER_KEY` | 로그인해야 할 운영 계정의 카페 회원 키; 닉네임 아님 |
| `FANART_STOP_FILE` | 존재하면 실행을 막는 중지 파일의 절대 경로 |
| `FANART_ASSETS_DIR` | 사이트와 공유하는 비공개 이미지 저장 경로 |
| `FANART_DATABASE_URL` | 팬아트 DB; 없으면 `ANALYTICS_DATABASE_URL`, 다음 `DATABASE_URL` 사용 |

프로필에는 로그인 정보가 저장됩니다. 저장소·Docker 빌드 컨텍스트·웹 공개 디렉터리 밖에 두고 운영 계정만 접근하도록 제한합니다. 평소 사용하는 개인 브라우저 프로필을 지정하거나 쿠키·비밀번호를 소스, 로그, 문서에 복사하지 않습니다. DB 연결 문자열도 문서나 명령 출력에 노출하지 않습니다.

경로 검증은 실제 경로를 확인합니다. 프로필·이미지·선택자·중지 파일용 **비공개 상위 디렉터리를 먼저 생성**해야 합니다. 대상 파일이나 프로필 자체는 아직 없어도 되지만, 상위 디렉터리가 없거나 저장소 내부를 가리키는 경로·링크는 거부합니다.

### 네이버 계정은 어떻게 연결하는가

서버에서 실행할 경우 필요한 것은 서버의 전용 브라우저 로그인 세션이다. 네이버 비밀번호를 `.env`나 프로그램에 저장하는 방식은 지원하지 않는다. 운영자가 그 브라우저에서 직접 로그인·추가 인증을 완료하고 비공개 프로필을 유지한다. 세션 만료 시 자동화를 중단하고 수동 재로그인한다.

개인 PC 브라우저와 서버의 세션은 별개이며 현재 브라우저의 쿠키를 추출·이전하지 않는다. 프로필도 계정 접근 권한을 포함하므로 운영 계정 전용 파일 권한과 접근 통제가 필요하다. 헤드리스 운영서버라면 직접 로그인할 수 있는 보호된 접속 환경을 별도로 구성해야 한다. 원격 데스크톱이나 디버깅 포트를 인터넷에 공개하지 않는다. 이번 코드 구현에서는 서버 로그인 환경을 설치하거나 계정을 연결하지 않았다.

`FANART_OPERATOR_MEMBER_KEY`는 로그인 여부를 대조할 카페 회원 식별자일 뿐, 비밀번호·인증 토큰의 대체물이 아니다. 아이디·비밀번호·쿠키·프로필 파일을 공개 문서나 채팅에 붙여 넣지 않는다.

브라우저 선택자 형식과 제약은 [브라우저 모듈 가이드](../frontend/scripts/fanart-browser/README.md)를 따릅니다. 댓글 로딩 완료, 페이지네이션, 부모 댓글 ID, 원작자 회원 키를 확실하게 확인할 수 없으면 활성화하지 않습니다.

## 실행 예시

아래 명령은 `frontend` 디렉터리에서 실행합니다. 필요한 환경 변수는 보안 설정으로 미리 전달합니다.

```powershell
npm ci
npx playwright install chromium

# 전용 브라우저에서 운영자가 직접 로그인
npm run fanart:outreach -- --login

# 로그인 계정과 설정된 원문 읽기 확인; 댓글 작성 없음
npm run fanart:outreach -- --inspect https://cafe.naver.com/moinge/10374

# 기본값: 처리 대상 확인만, 댓글/작품 상태 변경 없음
npm run fanart:outreach -- --once

# 댓글 작성 없이 답변 확인·승인 후 이미지 준비·최종 게시 처리
npm run fanart:outreach -- --once --apply

# 실제 댓글 전송을 명시적으로 허용: 최초에는 한 건만
npm run fanart:outreach -- --once --apply --send-comments --limit 1
```

`--apply`는 승인된 항목의 이미지 준비와 사이트 게시를 포함하는 실제 처리 모드입니다. 댓글만 막혀 있다고 읽기 전용으로 생각하면 안 됩니다. `--send-comments`는 `--apply`와 `--limit 1..5`가 함께 있어야 합니다.

기본 조회도 기존 저장소의 스키마 초기화와 DB 잠금을 사용할 수 있습니다. 작품 상태를 변경하지 않는다는 의미이지, DB 연결·스키마 초기화까지 전혀 하지 않는 무접속 검사 모드는 아닙니다.

반복 실행은 `--iterations`(최대 100)와 `--poll-seconds`(60~3600초)로 범위를 정합니다. 자동 작업 등록이나 운영 스케줄러 설치는 별도 운영 단계입니다. 댓글은 실행당 최대 5건, 계정별 최근 24시간 최대 10건, 요청 사이 최소 60초로 제한하며 DB 잠금으로 중복 작업자 실행을 막습니다.

`--limit`는 반복 횟수 전체에 적용되는 상한이지 발송 목표 수가 아닙니다. 한 차례 실행에서 다음 대상이 60초 제한에 걸리면 대기열에 남고, 작업자가 대상마다 60초를 기다려 모두 발송하지는 않습니다. `--inspect` 출력에는 회원 키와 답변 등 비공개 검토 정보가 포함되므로 공개 로그에 저장하지 않습니다.

## 중단·실패 대응

- 중지 파일을 생성하면 작업자가 다음 처리 또는 외부 쓰기 전 확인하여 멈춥니다. 이미 네이버에 전송된 댓글을 취소하는 기능은 아닙니다.
- 로그인 만료나 계정 불일치는 수동으로 다시 로그인하고 원문 조회를 확인한 뒤 재개합니다. 다른 계정을 임시로 허용하지 않습니다.
- `sending` 또는 `uncertain`은 자동 재전송하지 않습니다. 실행 중 프로세스가 종료되었거나 전송 결과가 불명확하면 네이버 원문과 식별표를 직접 확인합니다. 재전송을 위해 DB를 초기화하거나 후보를 중복 등록하지 않습니다.
- `needs_review`는 원문·이미지 URL·답변이 바뀌어 기존 확인이 무효화된 상태입니다. 다시 검토해야 합니다.
- 댓글 페이지네이션이 있거나 100개를 넘는 댓글, 20개를 넘는 이미지, 불명확한 회원/댓글 ID는 첫 버전에서 자동 처리하지 않습니다.
- 거절·철회된 작품은 작업자가 다시 공개하지 않습니다. 이미 공개된 작품의 허락 철회는 기존 관리자 철회 기능으로 즉시 처리합니다. 공개 후 답변 변경을 지속 감시하는 기능은 포함하지 않습니다.
- 작업자와 사이트가 다른 파일 시스템을 사용하면 준비 이미지가 보이지 않습니다. DB뿐 아니라 `FANART_ASSETS_DIR`의 실제 파일도 같은 저장소를 가리켜야 합니다.

## 관리자 API

기존 관리자 인증 및 변경 요청의 Origin 검사를 그대로 적용합니다. 응답과 미리보기는 `no-store`입니다.

- `POST /api/admin/fanart/{id}/outreach`: `action`, 현재 `version` 전달. 작업은 `enqueue`, `cancel`, `reject`, `confirm`, `approve`입니다.
- `confirm`: `confirmation`에 `replyId`, `imageId`, `display`, `resize`, `credit`, `nonAi`를 전달하며 확인 항목은 모두 실제 검토 후 `true`여야 합니다.
- `approve`: 미리 본 준비 파일의 `preparedHash`를 전달합니다. 같은 저장 트랜잭션에서 게시 대기 상태까지 기록합니다.
- `GET /api/admin/fanart/{id}/outreach/preview?sha256={preparedHash}`: 인증된 운영자만 준비된 정확한 이미지 파일을 봅니다.
- 버전 충돌은 새 상태를 불러와 다시 검토합니다. 오래된 화면의 승인 요청을 자동 반복하지 않습니다.

공개 갤러리에는 기존 공개 필드만 반환합니다. 작가의 답변 본문, 회원 식별자, 검토 근거와 브라우저 프로필 정보는 공개하지 않습니다.

## 검증 범위

자동 테스트는 가짜 브라우저 화면 및 로컬 테스트 DB로 수행합니다. 실제 네이버 댓글, 실제 작가 허락, 운영 사이트 게시 성공을 대신 검증하지 않습니다. 실제 계정·선택자 연결과 운영 배포 상태는 별도 검증 기록으로 확인해야 합니다.

`frontend/scripts/smoke-fanart-outreach.ts`는 로컬 테스트 서버와 실제 PostgreSQL, 가짜 카페 제공자, 자체 제작 도형을 연결해 관리자 화면을 검증합니다. `FANART_SMOKE_ALLOW_WRITES=true`, 루프백의 `/fanart_test` DB, 같은 비공개 이미지 디렉터리, 로컬 서버 URL이 필요합니다. 이 테스트를 운영 서버에 실행하지 않습니다.
