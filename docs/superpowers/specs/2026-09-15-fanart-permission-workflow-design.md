# 팬 커뮤니티 작업실 — 작품별 허락 기반 게시 설계

작성일: 2026-09-15

상태: 대화에서 승인된 기본 방향을 구체화한 설계서. 문서 검토 후 구현 계획을 작성한다. 아직 구현·수집·허락 요청 발송·운영 배포를 수행하지 않았다.

## 1. 목적과 승인된 방향

사용자는 팬카페의 생성형 AI가 아닌 이미지 작품을 참고해 작업실을 갱신하는 방안을 요청했으며, 기존 운영 방식은 작품 사용 전에 작가에게 개별 허락을 구하는 것이다.

1차 범위는 **원문 등록 → 허락 요청문 작성 → 동의·제작 방식 검수 기록 → 승인 후 자동 게시 → 철회**다. 자동화는 작가의 허락이나 운영자의 판단을 대체하지 않는다.

- 이미지의 공개 게시·크기 조정에 대한 작품별 허락을 기록한다.
- 작가의 생성형 AI 미사용 확인과 운영자의 검수 결과를 별도로 기록한다.
- 승인된 파일 처리와 목록 갱신은 자동화한다.
- 무응답, 불명확한 답변, 출처 불명은 승인으로 취급하지 않는다.
- 작가에게 메시지를 실제로 발송하거나 팬카페에 글을 작성하지 않는다.

## 3. 1차 기능과 제외 범위

### 포함

1. 관리자 전용 작품 원문 URL 등록 및 중복 확인.
2. 작가에게 보낼 허락 요청문 생성·복사. 실제 전송과 수신 확인은 운영자 담당.
3. 허락 범위, 확인일, 내부 증빙 메모, 제작 방식 검수 기록.
4. 허락·검수 조건 충족 후 운영자가 보유한 해당 작품 파일 업로드.
5. 파일 안전성 검사·리사이즈·메타데이터 제거·WebP 변환.
6. 명시적인 게시 승인과 작업실 자동 반영.
7. 게시 중단, 파일 접근 차단, 재등록 방지 기록.
8. 작가명·원문 링크·소개 날짜를 포함한 공개 갤러리.

### 제외

- 팬카페 로그인 크롤링, 비공개 게시물 수집, 자동 이미지 다운로드.
- 검색 API 연동, 정기 후보 검색, 예약 작업 생성.
- 작가에게 자동 메시지 발송, 답변 내용의 자동 승인 처리.
- AI 탐지 서비스, 작품의 외부 AI 서비스 전송, 작품 학습·재생성.
- 공개 제보 폼, 다중 운영자 계정 체계, 작가 계정 연동.
- 원본 다운로드 제공, GIF/애니메이션 게시, 주간 전시 큐레이션.
- 기존 팬아트 파일의 일괄 삭제 또는 허락 확인 없는 일괄 승인.

공개 제보 폼 대신 관리자 URL 등록으로 시작해 스팸·개인정보·추가 인증 범위를 줄인다. 작품별 파일은 1개로 제한하며, 동일 게시물의 여러 작품 지원은 후속 범위다.

## 4. 제작 방식과 이용 허락 기준

### 서로 독립적인 승인 조건

게시하려면 다음 조건을 모두 만족해야 한다.

- 작가명 또는 작가가 요청한 공개 표기명이 있다.
- 외부 사이트 `https://moingfans.com`에 작품을 표시하는 것을 허락했다.
- 사이트 표시용 크기 조정과 포맷 변환을 허락했다.
- 작가명·원문 링크 표기 방식을 확인했다.
- 작가가 해당 작품의 생성형 AI 미사용을 확인했다.
- 운영자가 제작 방식 검수를 완료했다.
- 허락과 검수 기록이 현재 파일 버전에 연결되어 있다.
- 승인 대상 파일이 안전성 검사를 통과했다.
- 철회 또는 거절 상태가 아니다.

1차 제작 기준은 생성형 AI로 생성하거나 실질적인 시각 요소를 생성·추가한 작품을 게시하지 않는 것이다. 일반 디지털 드로잉은 허용한다. 생성형 보정·업스케일링 등 사용 여부나 영향이 불명확하면 보류한다. 해시태그 부재나 메타데이터 부재만으로 미사용을 판단하지 않는다.

검수 결과는 `pending`, `confirmed_non_generative`, `unclear`, `excluded_generative`로 구분한다. 공개 화면에는 확인된 작품에만 **작가 확인·운영자 검수**라고 표시하며, 미승인 작가의 검수 사유는 공개하지 않는다. 이 표시는 완전한 진위 인증을 의미하지 않는다.

증빙은 확인 일시·대화 위치·필요한 최소 설명으로 기록한다. 비밀번호·로그인 쿠키·연락처 전체·대화 캡처는 저장하지 않는다. 공개 작업 과정 확인은 선택 사항이며 원본 작업 파일 제출을 일괄 요구하지 않는다.

## 5. 상태 전이와 운영 화면

관리 경로: `/admin/fanart`.

```text
후보 등록(candidate)
  → 허락 요청 기록(requested)
  → 조건 확인·파일 준비(ready)
  → 운영자 게시 승인(published)
  → 게시 철회(withdrawn)

candidate / requested / ready → 거절(rejected)
```

- `ready`는 서버가 승인 조건과 파일 존재를 검증해서 계산한다. 클라이언트가 상태 문자열만 보내 강제로 만들 수 없다.
- 공개 중 원문·작가·허락 범위·제작 확인·파일을 바꾸려면 먼저 게시 중단한다. 기존 승인을 새 파일에 승계하지 않는다.
- 철회·거절은 1차에서 최종 상태다. 동일 원문의 재등록을 막고 이전 레코드를 유지한다. 새로운 허락으로 재게시하는 절차는 후속 범위로 둔다.
- 게시 버튼 중복 클릭과 요청 재시도는 같은 결과를 반환한다.
- 동시 편집은 버전 번호를 비교하고 충돌 시 `409`와 새로고침 안내를 반환한다.
- 취소·검수 오류 메시지는 한국어로 제공하며 기술적 DB 오류나 증빙은 공개하지 않는다.

목록 화면에는 상태 필터, 제목, 작가, 원문 링크, 수정일을 제공한다. 상세 화면에는 요청문, 허락 항목, 검수 기록, 업로드, 게시·철회 버튼을 순서대로 배치한다. 파괴적인 게시 중단에는 대상 작품명을 확인하는 대화상자를 사용한다.

## 6. 데이터와 저장소

### PostgreSQL 카탈로그

기존 PostgreSQL 인스턴스를 사용하되 `fanart_works`와 `fanart_audit_events` 테이블을 분석 이벤트 테이블과 분리한다. 스키마 변경은 기존 테이블을 변경·삭제하지 않는 추가 방식이다.

`fanart_works`는 다음 정보를 갖는다.

- UUID, 정규화한 원문 URL, 원문 식별 키, 제목, 작가 표기명.
- 워크플로 상태, 버전 번호, 등록·수정·소개·철회 시각.
- 게시·리사이즈·출처 표기 동의, 동의 확인일, 내부 증빙 메모.
- 제작 방식 확인 상태·검수 메모·확인일.
- 현재 파일 식별자·SHA-256·크기·너비·높이 및 승인 대상 파일 해시.

감사 기록은 후보 생성, 요청 기록, 허락/검수 변경, 파일 준비, 게시, 철회를 서버 시각과 함께 남긴다. 현재 단일 관리자 인증이므로 개별 사람을 식별하는 다중 사용자 감사 기능이라고 표현하지 않는다.

공개 응답은 `id`, `src`, `alt`, `credit`, `sourceUrl`, `publishedAt`만 포함한다. 내부 증빙·검수 메모·관리 상태·파일 경로는 반환하지 않는다. 다운로드 URL은 제공하지 않는다.

### 이미지 저장

- 신규 전용 영속 볼륨 `fanart_assets`를 사용한다. `public/rightAside` 및 Git에 신규 파일을 넣지 않는다.
- 컨테이너 경로는 `/app/data/fanart`; 개발 환경은 저장소에서 제외한 로컬 데이터 디렉터리를 사용한다.
- 허락·제작 확인을 마친 운영자 업로드만 받는다. 외부 URL을 서버에서 가져오는 기능은 제공하지 않는다.
- 입력 PNG/JPEG/WebP, 파일당 10 MiB 이하, 총 픽셀 수 2,000만 이하, 프레임 1개만 허용한다.
- `sharp`로 디코딩 검사 후 최대 긴 변 1600px, 확대 없음, WebP 변환 및 EXIF 등 메타데이터 제거. 출력이 5 MiB를 넘으면 등록하지 않는다.
- 클라이언트 파일명이나 MIME을 저장 경로·검증의 근거로 신뢰하지 않는다. 서버 생성 식별자로 저장한다.
- 변환된 파일을 먼저 안전하게 저장하고 트랜잭션으로 메타데이터를 연결한다. 실패한 업로드는 게시 목록에 영향을 주지 않는다.
- 영속 볼륨의 컨테이너 사용자 쓰기 권한과 백업·복원 절차를 배포 전 검증한다.

## 7. API 계약과 보안

| Method / 경로 | 계약 |
|---|---|
| GET `/api/admin/fanart` | 관리자 목록, 페이지 크기 최대 50 |
| POST `/api/admin/fanart` | 원문 URL·제목·작가로 후보 생성, `201`; 중복 `409` |
| GET `/api/admin/fanart/[id]` | 관리자 상세와 기록 |
| PATCH `/api/admin/fanart/[id]` | 허락·검수 기록 수정, 예상 버전 필수 |
| POST `/api/admin/fanart/[id]/asset` | 조건 충족 후 제한된 multipart 파일 업로드 |
| POST `/api/admin/fanart/[id]/publish` | 서버 조건 재검증, 파일 해시를 승인에 결합 |
| POST `/api/admin/fanart/[id]/withdraw` | DB 상태 변경과 공개 접근 차단 |
| GET `/api/fanart` | 공개 승인 목록만, 최대 24개, 소개일 내림차순 |
| GET `/media/fanart/[id]` | 매 요청 게시 상태·승인 해시 검증 후 변환 이미지 제공 |

- 관리 API와 페이지 모두 기존 Basic Auth로 보호한다. 새 쓰기 API는 개발 환경을 포함해 자격 증명이 없으면 비활성화한다.
- Basic Auth가 CSRF를 막아주지 않으므로 쓰기 요청은 설정된 사이트 origin과 정확히 일치하는 `Origin`을 요구하고 누락·불일치를 `403`으로 거부한다. 허용 origin은 요청의 Host 헤더만으로 결정하지 않는다.
- JSON 본문은 32 KiB, 업로드 본문은 11 MiB로 스트림 읽기 단계에서 제한한다. Content-Length만 신뢰하지 않는다.
- 텍스트는 길이를 제한하고 React 일반 문자열로 표시한다. SQL은 매개변수 바인딩한다.
- URL은 HTTPS, NAVER 카페의 지정 호스트·모잉 카페 경로만 허용한다. 사용자 정보, 임의 포트, 위장 도메인을 거부한다.
- 1차 지원 URL은 `https://cafe.naver.com/moinge/{articleId}`와 `https://cafe.naver.com/f-e/cafes/30182989/articles/{articleId}`로 제한한다. 쿼리와 fragment를 제거하고 `30182989:{articleId}`로 중복 판정한다. 다른 공유 링크는 운영자에게 지원 형식으로 변환하도록 안내한다.
- 회원 전용 원문도 로그인 우회 없이 작가 허락을 별도로 확인한다. 외부 이미지 게시가 카페 접근 범위를 넘어서는 점을 작가에게 설명해야 한다.
- 관리·공개 동적 응답과 이미지 경로에는 `Cache-Control: no-store`를 적용한다. 이미지에는 정확한 Content-Type과 `X-Content-Type-Options: nosniff`를 설정한다.
- 동일 조건을 통과하지 못한 미게시·철회 이미지 직접 요청은 `404`다. DB 상태 확인 실패 시 `503`이며 파일을 제공하지 않는다.

## 8. 공개 화면, 캐시, 장애 처리

신규 승인 작품은 별도의 클라이언트 목록 로딩으로 홈페이지와 사이드바에 동일하게 전달한다. 최초 방문·포커스 복귀·60초 간격으로 재확인하며 탭이 숨겨지면 주기 요청을 멈춘다. 홈페이지의 다른 섹션과 ISR 정책을 변경하지 않는다.

갤러리와 모달은 서버에서 이미 최적화한 신규 이미지를 사용한다. 신규 이미지 경로에 Next.js 이미지 최적화 캐시를 거듭 적용하지 않도록 `unoptimized`로 표시해 철회된 이미지가 최적화 캐시에서 계속 제공되는 것을 피한다. 새 목록에서 현재 작품이 없어지면 유효한 항목으로 이동하고, 빈 목록에서는 모달을 닫는다.

빈 상태 문구는 "작가의 사용 허락과 검수를 마친 작품을 소개합니다"로 바꾼다. 카페에 업로드하면 무조건 소개된다는 기존 안내는 제거한다.

철회 성공은 DB에 철회 상태가 저장된 뒤 반환한다. 이후 신규 이미지 요청은 즉시 차단되며 열린 페이지는 다음 목록 확인 시 반영된다. 이미 이용자가 저장했거나 브라우저에 표시 중인 이미지까지 원격으로 회수할 수 있다고 약속하지 않는다.

수집 기능이 없는 1차에서는 외부 원문 장애가 전시 상태를 바꾸지 않는다. 카탈로그 갱신 실패는 DB의 게시 기록을 삭제하지 않는다. 다만 권한을 재검증할 수 없는 신규 이미지 요청은 보수적으로 중단한다. 실패 응답을 정상 빈 목록으로 저장하거나 자동 철회 처리하지 않는다.

### 기존 파일과의 전환

기존 `public/rightAside` 파일은 이번 변경으로 삭제하거나 자동 승인하지 않는다. 신규 동적 카탈로그와 명확히 구분된 기존 목록으로 유지하며 '작가 확인·운영자 검수' 표시는 신규 승인 작품에만 적용한다.

기존 파일을 신규 카탈로그로 옮길 때는 작품별 허락 기록을 등록하고 해당 정적 파일과 참조를 제거하는 별도 변경이 필요하다. 이전 URL과 이미지 최적화 캐시를 포함한 철회 범위를 그때 검증한다. **신규 관리 화면의 철회 기능이 기존 정적 파일에도 소급 적용된다고 안내하지 않는다.** 신규 파일의 오류를 이유로 철회된 신규 작품을 정적 목록에서 복구하지 않는다.

## 9. 구현 단위와 검증 기준

구현 계획은 아래 순서로 테스트 실패 확인 → 최소 구현 → 회귀 검증을 반복한다.

1. `frontend/app/lib/fanart/`에 공유 타입, URL 정규화, 승인 조건, 요청문, 상태 전이 로직.
2. 전용 테이블 저장소와 트랜잭션·동시성·중복·감사 기록 검증.
3. 관리자 인증·Origin·본문 제한, 관리 API와 이미지 업로드 처리.
4. 공개 목록·이미지 서빙·철회 차단과 갤러리 통합.
5. 관리자 화면, 영속 볼륨 설정, 운영 문서와 브라우저 테스트.

필수 자동 테스트:

- 미허락, 미검수, 불명확한 AI 사용, 파일 없음, 철회 상태에서는 게시 불가.
- 파일 교체·원문 변경이 이전 승인을 이어받지 않음.
- 인증 누락, 잘못된 Origin, 과대 본문, 위장 이미지, 경로 조작 거부.
- 동일 원문 URL 변형 중복 방지, 중복 게시 요청 멱등성, 동시 수정 충돌.
- 공개 API에서 내부 증빙·메모·파일 경로 노출 없음.
- 철회 후 목록 제외 및 이미지 직접 접근 차단; DB 실패 시 이미지 비공개 유지.
- 게시 중단과 이미지 요청 경쟁 상황의 허용 범위를 확인: 철회 커밋 이후 시작한 요청은 파일을 받지 못함.
- 변환·DB 저장 실패가 기존 승인 목록을 손상하지 않음.
- 컨테이너 재생성 후 카탈로그·파일·철회 상태 보존.

브라우저 테스트는 권리를 보유한 자체 테스트 도형으로 수행한다. 등록부터 허락 기록·업로드·게시·갤러리 원문 이동·철회까지 확인하고, 목록이 줄어들 때 모달과 자동 슬라이드가 깨지지 않는지 검증한다. 실제 작가 작품으로 시험 게시하지 않는다.

정적 검증은 `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`를 수행한다. PostgreSQL 통합 테스트와 Docker 런타임 검증은 실행 여부와 실제 결과를 분리해 기록한다. 테스트 환경이 없으면 통과했다고 보고하지 않는다.

## 10. 출시와 후속 범위

현재 사용자 요청은 승인형 흐름 진행이다. 이 설계 문서 작성만으로 배포·실제 작품 사용·메시지 발송 승인을 추정하지 않는다.

구현 후에는 변경 내용, 테스트 결과, 관리자 설정, DB/볼륨 백업, 롤백 시 신규 작품 접근에 미치는 영향을 문서화한다. 실제 운영 반영 전에는 배포 요청과 정상적인 릴리스 검증이 필요하다.

2차 후보 검색은 별도 설계로 다룬다. 네이버 카페 검색 API는 제목·링크·요약 등을 반환하지만 이미지 파일 및 전체 본문을 제공하지 않으며 완전한 게시판 수집을 보장하지 않는다. 자동 검색을 도입하더라도 후보 등록까지만 수행하고 승인 조건은 그대로 유지한다.
