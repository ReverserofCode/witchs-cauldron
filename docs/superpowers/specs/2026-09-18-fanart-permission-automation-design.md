# 팬카페 이용 허락 요청 및 승인 후 게시 자동화 설계

작성일: 2026-09-18. 상태: 사용자가 권장 운영 방식을 승인하고 정책 확인을 개발 선행 조건으로 두지 말고 구현하도록 지시함. 실제 계정 연결·화면 검증·댓글 발송·배포는 개발 검증과 구분한다.

## 실행 범위 보완 (사용자 후속 지시)

- 정책 확인은 기술 개발의 차단 조건에서 제외한다. 아래 공식 문서 조사 결과 자체를 삭제하거나 승인받은 것으로 바꾸지 않는다.
- 첫 버전은 운영자가 등록한 원문 후보를 처리하는 별도 브라우저 실행기다. 과거 글 일괄 발송과 모든 새 글의 자동 발견은 제공하지 않는다. 후보 등록 이후 댓글 작성·답변 수집·승인 후 게시를 자동화한다.
- 별도 브라우저 프로필에 사용자가 직접 로그인한다. 일반 브라우저 쿠키/비밀번호를 추출하지 않는다. 네이버 화면의 선택자는 설정 파일로 명시하고, 필수 요소·작성자·대상 게시판 확인 실패 시 중지한다. 비공개 HTTP API나 CAPTCHA 우회는 사용하지 않는다.
- 실제 카페 화면에 대한 로그인 상태의 검증이 없으므로 테스트용 DOM과 운영 검증을 구분하며, 테스트 선택자를 실제 네이버 선택자로 가장하지 않는다.
- 파일 동일성을 보장하기 위해 관리자가 이용 허락·제작 방식을 확인하면 파일을 비공개로 자동 준비하고, 준비된 이미지의 최종 확인 후 자동 게시한다. 허락 기록 저장과 공개 게시 승인 버튼을 분리한다. 기존 단일 이미지 정책은 유지한다.
- 브라우저 실행기는 기본 읽기/미리보기 모드다. 댓글 쓰기는 명시적 실행 옵션, 계정 식별자, 양수 한도, 관리자가 대기열에 넣은 대상이 모두 있을 때만 가능하다. 이번 개발 중 실제 카페 댓글 발송과 운영 게시를 하지 않는다.
- 다음 구현 계획의 실행 범위 보완이 아래 초기 설계와 충돌하면 이 보완을 우선한다. 초기의 플랫폼 사전 허락 확인 게이트, 자동 후보 발견, 원격 이미지 식별만으로 최종 승인하는 부분은 위 방식으로 대체한다.

## 1. 목표와 결정

사용자가 승인한 목표는 팬카페 게시물 후보 발견 → 이용 허락 댓글 자동 작성 → 답변 수집 → 관리자의 허락 판단 → 승인된 이미지 자동 등록·moingfans 게시다.

사람이 하는 핵심 작업은 답변 작성자, 이용 범위, 비AI 제작 확인, 사용할 이미지, 공개 표기명을 확인하고 `확인 후 자동 게시`를 누르는 것이다. 동의 여부를 AI가 결정하지 않는다. 앞서 제안한 다중 이미지 작품집은 별도 후속 과제로 미룬다. 1차 범위는 기존 모델과 동일하게 원문당 대표 이미지 1개다.

## 2. 공식 문서에서 확인된 선행 조건

2026-09-18 확인:

- [네이버 게시물 운영정책](https://policy.naver.com/rules/service_group.html)은 네이버의 사전 허락 없는 자동화 수단을 통한 게시를 제한 대상으로 명시한다. 확인한 정책 시행일은 2026-07-07이다.
- [네이버 공개 API 목록](https://developers.naver.com/docs/common/openapiguide/apilist.md)의 카페 항목은 가입과 게시글 작성 API를 설명한다. 댓글 작성·댓글 조회 기능은 이 공개 목록에서 확인되지 않았다. 게시글 작성 API를 댓글 API로 취급하지 않는다.
- [카페 API 소개](https://developers.naver.com/products/login/cafe/cafe.md) 역시 가입과 게시글 작성을 소개한다. 계정 로그인 또는 카페 가입만으로 댓글 자동화 가능 여부를 확인한 것은 아니다.

따라서 현재 근거만으로 운영 자동 댓글 발송·답변 수집을 구현 가능하다고 확정할 수 없다. 네이버의 허용 근거와 실제 사용할 연동 규격, 카페 운영자의 운영 방침을 확인해야 한다. 카페 운영자의 허락과 네이버의 사전 허락은 별개이며, 작가의 이미지 사용 허락도 별도로 필요하다.

권한 확인 전에는 외부 연동을 비활성화하고 로컬 모의 제공자로만 검증한다. 비공개 API 추정, 로그인 쿠키 추출, CAPTCHA·접근 제한 우회, 다중 계정 발송은 설계에 포함하지 않는다. 자동 댓글 대신 수동 댓글로 범위를 바꾸는 것은 사용자에게 별도 동의를 받는다.

## 3. 현재 시스템 연결 지점

- `frontend/app/lib/fanart/model.ts`: 허락·비AI 제작 확인·운영자 검수, 원문 정규화, 상태 전이, 요청문 생성.
- `frontend/app/lib/fanart/repository.ts`: 원문 중복 방지, PostgreSQL 저장, 버전 충돌 방지, 감사 기록.
- `frontend/app/lib/fanart/assets.ts`: 제한된 이미지 형식·용량, 변환, 해시 검증, 비공개 볼륨 저장.
- `frontend/app/lib/fanart/handlers.ts`: 관리자 인증·Origin 검증, 업로드와 게시의 최종 검증.
- `/admin/fanart`: 기존 수동 관리 기능은 계속 제공한다.
- 기존 백엔드 클립 작업 관리자는 메모리 상태를 사용하므로 장기간 답변 대기·재시작 복구가 필요한 허락 작업에 그대로 재사용하지 않는다.

## 4. 구성과 책임

1. **카페 연동 어댑터**: 허용된 범위의 후보 조회, 댓글 작성, 답변 조회, 승인 대상 이미지 접근. 실제 전송 방식은 승인된 규격 확인 후 정한다. 각 기능의 지원 여부를 개별 선언하며 미지원 기능은 차단한다.
2. **요청·답변 저장소**: 원문 ID, 작성자 식별자, 댓글 ID, 요청문 버전, 답변 변경 이력, 발송 결과를 PostgreSQL에 보관한다.
3. **관리자 검토함**: 요청 내용과 작성자 답변을 함께 표시하고 이미지·허락 범위를 관리자가 확정한다.
4. **자동 게시 작업자**: 관리자 결정에 연결된 작업만 가져와 승인된 파일을 검증·변환·저장하고 기존 게시 정책을 거쳐 공개한다.

작업자는 관리자 Basic Auth 비밀번호를 공유받아 공개 API를 호출하는 방식으로 만들지 않는다. 기존 정책을 공통 서버 서비스로 분리해 사용한다. 관리자 UI 인증과 Origin 검증은 그대로 유지하고, 작업자는 별도 서비스 프로세스 및 최소 권한으로 실행한다.

## 5. 후보와 댓글 정책

- 범위: 카페 `30182989`, 팬아트 게시판 `38`. 다른 게시판·카페로 자동 확장하지 않는다.
- 명시적 AI 표기나 제작자 AI 사용 설명이 있는 후보는 제외한다. 표기가 없다는 이유로 비AI 확정 처리하지 않는다.
- 과거 글 전체에 소급 발송하지 않는다. 초기 대상은 운영자가 선택한 소수 원문이며, 신규 글 자동 발견은 연동 승인 범위 내에서 별도 활성화한다.
- 댓글에는 운영 주체, `https://moingfans.com`, 대상 이미지, 표시·크기 조정·WebP 변환·작가명·원문 링크 범위, 비AI 제작 여부 질문, 철회 방법을 명시한다. 임의의 비상업성 주장이나 검증되지 않은 약속을 추가하지 않는다.
- 원문당 최초 허락 요청은 1회. 무응답 재촉과 거절 후 재요청은 하지 않는다. 작가별 요청 거부 목록을 유지한다.
- 발송 속도·일일 한도는 네이버의 허용 범위와 카페 운영자 합의 후 설정한다. 미설정 기본값은 발송 0건이다.
- 전송 타임아웃처럼 실제 작성 여부가 불명확하면 `발송 결과 확인 필요`로 보류한다. 무조건 재시도하지 않고 원격 댓글 ID 또는 승인된 조회 수단으로 확인한다.
- 활성화·일시정지·대기열 취소·긴급 중지 기능을 제공한다. 중지 시 이미 발송된 댓글을 자동 삭제하지 않는다.

## 6. 관리자 확인과 게시 흐름

허락 요청의 상태와 기존 작품 상태를 분리해 기존 API의 상태값을 불필요하게 변경하지 않는다.

`후보 → 요청 대기 → 요청 완료 → 답변 대기 → 관리자 확인 대기 → 게시 대기 → 게시 완료`

예외 상태: 제외, 거절, 발송 결과 확인 필요, 접근 차단, 원문 변경, 재검토 필요, 게시 실패, 철회.

관리자는 한 화면에서 다음을 확인한다.

- 답변자가 원문 작성자이며 이용 허락을 할 수 있는 당사자인지.
- 외부 게시·이미지 변환·작가 표기 범위와 특별 조건.
- 생성형 AI 미사용에 대한 작가 확인 및 운영자 검수.
- 사용할 대표 이미지 한 장과 작가가 원하는 공개 이름.
- 승인할 원문·답변 버전과 시각. 다른 사람의 답변이나 모호한 답변은 승인하지 않는다.

관리자의 결정은 증빙 버전과 이미지 식별자에 묶인 불변 기록으로 저장한다. 결정과 게시 작업 생성은 같은 DB 트랜잭션으로 처리한다. 작업자는 현재 상태를 재검사하고 승인된 대상만 한 번 게시한다. `확인 후 자동 게시`는 명시적인 게시 지시이며 단순 검토 메모 저장과 구분한다.

## 7. 승인된 이미지 가져오기

- 허락 확인 전에는 이미지 파일을 프로젝트 저장소·운영 볼륨에 수집하지 않는다. 관리자는 원문에서 작품을 확인한다.
- 승인된 연동이 제공한 안정적인 첨부 식별자·리비전 등으로 파일 일치성을 확인할 수 있을 때만 승인 후 자동 가져오기를 허용한다. 순번이나 변경 가능한 URL만으로 동일 파일이라고 간주하지 않는다.
- 대상 이미지가 수정되었거나 일치성을 검증할 수 없으면 자동 게시를 중단하고 재검토한다. 안전한 첨부 식별 기능이 없는 제공자라면 승인 후 비공개로 준비한 파일을 관리자가 최종 확인해야 하며, 이 추가 단계를 숨기지 않는다.
- HTTPS 및 승인된 제공자의 검증된 이미지 호스트만 허용한다. 임의 URL 입력을 통한 서버 요청은 금지한다. 리다이렉트·DNS·사설망 주소를 검사하고 인증 정보는 이미지 호스트로 전달하지 않는다.
- 기존 제한(입력 10 MiB·2천만 픽셀, 출력 긴 변 최대 1600px·WebP 5 MiB)을 유지한다. 다운로드 시간·수신 바이트 상한을 스트리밍 단계부터 적용한다.
- 변환 및 파일 해시 확인 후 기존 공개 정책으로 게시한다. 불완전한 파일이나 실패한 작업은 공개 목록에 포함하지 않는다.

## 8. 재시도·변경·철회

- DB 기반 작업 큐와 작업 임대 만료로 서버 재시작 후 복구한다. 관리자 승인 ID에 고유 제약을 두어 중복 클릭·재실행으로 중복 게시되지 않도록 한다.
- 외부 쓰기의 정확히 한 번 실행을 보장한다고 주장하지 않는다. 불명확한 발송 결과는 자동 재전송하지 않는 정책으로 중복을 방지한다.
- 승인 후 답변·원문 변경이 확인되면 게시 대기 작업을 취소하고 재검토한다. 이미 공개된 작품의 허락 철회 가능성을 감지하면 관리자 확인 전 임시 비공개하는 별도 보류 상태를 설계하고 기존 불가역 철회와 구분한다.
- 로그인 만료·접근 제한·인증 요청에서는 해당 연동을 중지하고 관리자에게 알린다. 정상 권한으로 사용자가 직접 해결한 뒤 재개한다.
- 기존 공개 API의 개인정보 배제·no-store·이미지 해시 검증 및 철회 후 미디어 차단은 유지한다.

## 9. 검증과 단계별 도입

1. 모의 제공자: 중복 후보, 거절, 무응답, 다른 작성자 답변, 조건부 허락, 원문/답변 수정, 타임아웃 후 중복 발송 방지.
2. 일회성 DB: 승인·작업 생성의 원자성, 동시 승인, 중복 실행, 재시작 복구, 취소와 게시 경합.
3. 이미지 보안: 임의 URL, 사설망·리다이렉트, 과대 파일, 이미지 교체, 해시 불일치, 허락 전 수집 방지.
4. 브라우저: 관리자 확인 1회 후 게시 완료까지 진행, 실패·보류 사유 표시, 기존 수동 기능·갤러리·철회 회귀.
5. 승인된 시험 환경: 실제 연동 규격으로 댓글 ID 반환·답변 작성자 식별·이미지 대상 고정 검증. 허락 없는 실제 작품과 계정으로 시험하지 않는다.
6. 운영: 네이버·카페의 허용 범위, 사용할 계정, 최종 댓글 문구, 대상 범위, 한도, 긴급 중지를 확인한 뒤 제한적으로 활성화한다. API·모의 테스트 통과만으로 실제 카페 연동 완료라고 보고하지 않는다.

## 10. 다음 결정

네이버의 댓글 자동 작성·답변 수집에 대한 사전 허락 또는 승인된 연동 수단이 확보되어 있는지 사용자 확인이 필요하다. 현재는 미확인 상태다.

확보된 경우 해당 범위와 기술 문서를 기준으로 상세 구현 계획을 작성한다. 확보되지 않은 경우 자동 댓글을 가동하지 않고, 허용 연동 확보 또는 별도 승인을 받은 수동 댓글·관리자 확인 후 내부 게시 자동화 중 다음 경로를 정한다. 사용자 동의 없이 원래 목표를 수동 방식으로 바꾸지 않는다.
